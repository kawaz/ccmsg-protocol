# DR-0031: `file.read` はバイト列を範囲で答える

- Status: Active — ⬜ 未実装
- Date: 2026-09-19

## Context

今の `file.read` はテキストを 1 回で全部渡す形で、`src/control/files.ts` の `FileReadResult` はそれをそのまま述べている。

- `content: string` — 文字列。バイト列を運ぶ器が無い
- `binary: boolean` — 「頭を嗅いだらバイナリだったので**テキストは送らない**」。この時 `content` は空で、**呼び手はその中身を一切受け取れない**
- `truncated: boolean` — instance の読み取り上限で切れた印
- 引数は `sid` / `kind` / `path` だけで、**続きを求める術が無い**

つまり画像も PDF も動画も、契約の上では「読めないと答えるだけの物」になっている。webui の Files の画面にも「`file.read` は続きを求める引数を持たないので、この先はここからは読めません」という文言が既に出ていて、切れた大きなテキストの続きも読めない。

ここを開けたい理由は、人が接続中のセッションの手元にあるファイルを**ブラウザに素で描かせて見たい**から (ccmsg-webui `docs/decisions/DR-0005-a-viewing-site-draws-files-through-a-service-worker.md`)。描くのはブラウザなので、要るのは「そのファイルのバイト列を、ブラウザに渡せる大きさに割って取れること」だけで、描き方も置き場も契約の話ではない。

もう 1 つの制約が [DR-0016](DR-0016-limits-the-sender-keeps-to.md) の `MAX_FRAME_BYTES` (1 MiB)。1 行に収まらない物は**運べない**のだから、大きなファイルを 1 回で渡す形はそもそも取れない。範囲読みは「あると便利」ではなく、バイト列を足すなら同時に要る対の片割れ。

## Decision

### 1. 答えはバイト列で、テキストはその読み方の 1 つ

`FileReadResult` の `content: string` を、**バイト列を運ぶ 1 つの器**に置き換える。器は base64 の文字列 1 本で、テキストかどうかで綴りを変えない。

- `binary` は残すが、意味を **「中身を送らない印」から「テキストとして読むな、という印」** に変える。`binary` が真でもバイト列は渡る
- `encoding` のような分岐を足さない。**常に base64** で、呼び手は常に同じ復号を通す。「テキストなら生、そうでなければ base64」にすると呼び手が 2 経路を持ち、しかも分岐の判定を受け手の嗅ぎ分けに委ねることになる

`MAX_FRAME_BYTES` に対する予算はこの選択で決まる。base64 は 4/3 に膨らむので、**1 回の応答が運べるのは 512 KiB のバイト列まで**とする (base64 で約 683 KiB、envelope と path の余地を残して 1 MiB の内側)。これが後述の `length` の既定であり上限。

### 2. 範囲は `offset` と `length` で頼み、答えは自分がどこを答えたかを述べる

- 引数に `offset` (先頭からのバイト、既定 0) と `length` (バイト数、既定かつ上限 512 KiB) を足す
- 結果は `offset` と、実際に返したバイト数を述べる。`size` は**ファイル全体の大きさ**のままで、これと合わせれば呼び手は「続きがあるか」を引き算で言える
- **`truncated` は廃止する**。「上限で切れた」は `offset + 返したバイト数 < size` と同じことで、2 つの言い方を持つと片方が嘘をつく。境界を跨ぐ読み方をした呼び手が、切れたのか終端なのかを印ではなく数で判断できる方が確か
- 範囲がファイルの終端を越えていたら、**重なっている分だけを返す**。完全に外なら 0 バイトを返し、誤りにはしない — 終端まで読み進める呼び手が最後に必ず踏む所なので、そこを誤りにすると正常な読みが誤りで終わる
- 読んでいる間にファイルが変わった時の扱いは `mtime_at` が既に持っている。範囲読みは**その場その場の読み**で、契約は一貫した snapshot を約束しない (§5)

### 3. 何のバイト列かは、契約は答えない

結果に media type (MIME) を足さない。instance が持っているのは**バイト列とパスだけ**で、それが何として描かれるべきかは描く側の判断。拡張子からの推測も、頭のバイトからの嗅ぎ分けも、**やるなら呼び手がやる**。

足す形も検討した — 結果に `media_type` を 1 つ添え、instance が拡張子か頭のバイトから決めて名乗る。呼び手はそれを `Content-Type` にそのまま載せればよく、**判定の表が呼び手ごとに重複しない**のが利点。

採らないのは、**その値が描画の性質を決めてしまう**から。`Content-Type` は「このバイト列を何として扱うか」であり、`text/html` と名乗れば script が走り、`application/octet-stream` なら走らない。instance の嗅ぎ分けを描画に直結させると、**嗅ぎ分けの誤りが描く側の安全性の判断になる**。描く責務を持つ側が、自分の危険の度合いに合わせて決める方が境界として正しい (この判断に乗っている側の書き方は ccmsg-webui DR-0005 §2.3)。

重複の代償も小さい。判定の表が要るのは**描く呼び手だけ**で、読んで解析するだけの呼び手には最初から要らない。

### 4. transport は選ばない

バイト列は応答の本文に載る。**WS の text frame でも、将来の DataChannel でも、同じ envelope の同じフィールド**として渡る。binary frame や別の side channel へ切り出す形は採らない ([不採用](#不採用))。

## 不採用

| 採らなかったもの | なぜ |
|---|---|
| **バイト列を WS の binary frame で側送りする** | transport ごとに運び方が分かれる。DataChannel でも、まだ見ぬ transport でも「その transport の binary な運び方」を都度決めることになり、契約が 1 つの形を持てなくなる。base64 の 33% は、その代償としては安い |
| **テキストは生の文字列、バイナリだけ base64** | 呼び手が常に 2 経路を持つ。しかも「どちらで来るか」を決めるのは受け手の嗅ぎ分けなので、呼び手は自分が頼んだ物の形を頼む前には知れない |
| **`file.read` を残したまま `file.read_bytes` を足す** | 同じ問い (このパスの中身) に op が 2 つ。テキストの範囲読みも要る以上、2 つは機能でも分かれず、片方にだけ足された引数が生まれる ([DR-0017](DR-0017-one-generation-no-compatibility-path.md): 互換経路を持たない) |
| **`truncated` を残す** | 「切れた」と「数を見れば分かる」の二重表現。範囲読みが入ると `truncated` は「頼んだ範囲より短かった」の意味になり、終端に届いた正常な読みでも真になる。印の意味が読み方によって変わる |
| **結果に media type を足す** | instance の嗅ぎ分けが、描く側の描画の性質 (script が走るかどうか) を決めてしまう。判定の表が重複する不利益より、境界の方が重い (§3) |
| **範囲がファイルの外なら `bad_request`** | 終端まで読む呼び手が最後に必ず踏む。正常な読みの終わりを誤りで表すことになる |
| **範囲ではなく「続きの token」を返す** | 順に読む呼び手しか居ないなら等価だが、描く側は**飛び飛びに読む** (HTTP の Range を SW が受ける)。token は前から順にしか進めない |
| **上限を instance の設定にする** | 呼び手は 1 回で何バイト頼めるかを知らないまま頼むことになる。`MAX_FRAME_BYTES` から導けるのだから、導いた値を契約が述べる ([DR-0016](DR-0016-limits-the-sender-keeps-to.md) と同じ線) |

## 帰結

- **バイナリを「読めない物」として扱う経路が契約から消える**。`binary` はテキストとして読むなという注意書きになり、中身は常に渡る
- 呼び手は常に base64 を復号する。テキストだけを読んでいた既存の呼び手 (webui の Files) も復号を通すようになる
- 大きなファイルは**複数往復**になる。1 回の往復が 512 KiB なので、10 MiB の動画は 20 回。要求は並行に走れる ([DR-0002](DR-0002-request-id-and-concurrency.md)) ので直列に待つ必要は無いが、**往復の数だけ帯域と遅延が効く**形は変わらない
- 読んでいる最中のファイルの変更を、契約は隠さない。範囲ごとに `mtime_at` が返るので、呼び手は**変わったことに気付ける**が、変わらないことは保証されない (§5)
- fixtures ([DR-0024](DR-0024-executable-contract-and-fixtures.md)) に、バイナリの 1 範囲と、終端を跨ぐ範囲の代表例が要る

## 前提

| 前提 | 満たさない場合 |
|---|---|
| 1 行 1 MiB (`MAX_FRAME_BYTES`) が変わらない | 変われば 512 KiB の根拠も変わる。上限は `MAX_FRAME_BYTES` から導いた値として書き、独立した定数として持たない |
| 読み手はバイト列を base64 で扱える | ブラウザにも Bun にもある。無い呼び手が出たら、それはこの契約の対象外の環境 |
| ファイルは読んでいる間おおむね動かない | 動く物 (書かれ続けるログ) を範囲で読むと、範囲の継ぎ目が食い違う。契約はそれを検出する材料 (`mtime_at`) を渡すだけで、一貫した読みは約束しない。必要なら別の問い (追記の購読) であって、`file.read` の仕事ではない |

## 要裁定

裁定に無く、実装に入る前に決めたい点。**ここでは決めない**。

| | 問い | なぜ要るか |
|---|---|---|
| RB-Q1 | `length` の既定を 512 KiB (上限と同値) にするか、もっと小さくするか | 既定を上限と同値にすると、小さなファイルを読む呼び手が何も考えずに済む。一方で「とりあえず読む」が常に最大の frame を作る。§1 は同値で書いてあるが、根拠は「余計な引数を書かせない」だけで強くない |
| RB-Q2 | `file.write` / `file.create` / `file.edit` の `content` も同じ器に揃えるか | 読みだけバイト列になると、**読めるが書き戻せない形**のファイルが生まれる。揃えるのが素直だが、書き込みは本 DR の目的 (閲覧) の外で、[DR-0017](DR-0017-one-generation-no-compatibility-path.md) の下では同じ世代で両方を変えるのが自然という以上の理由が今は無い |
| RB-Q3 | 範囲読みの最中にファイルが変わったことを、呼び手が**確実に**知る手立てが要るか | §2 は `mtime_at` を毎回返すので気付けるが、粗い時計では気付けない (`file.edit` が `expected_size` を併せて持つのと同じ穴)。閲覧は使い捨てなので実害は薄いが、穴が残ること自体は書いておく |
